# Schema administration

Schema managers can create and edit collection settings, add all 17 pinned field types, edit existing field metadata, reorder collections and fields, and delete fields or collections. These controls extend the [historical bounded administration](schema-admin.md) and the [persisted schema domain](full-schema.md). They use the configured runtime and trusted server permissions; credential setup/login remains a separately reviewed feature.

Authority is EmDash **1.1.0**, immutable [`913cb1bb9b7f08c3ff0d258b4420e53835b6a58e`](https://github.com/emdash-cms/emdash/commit/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e). Integration base is verified CMS main `2aaea79a017fad543e1b462a4a3c48410366a04c`, after runtime36 and typed transport43. Keep the [MIT notice](../notices/emdash-MIT.txt). This feature is proposed in [PR #49](https://github.com/sveltery/cms/pull/49), with independent/configured review and final-head checks before PM approval and developer merge; none is inferred from the previous domain PR.

## Available controls

Collection forms expose all six support flags, icon, navigation group, URL pattern, routability, SEO, hidden navigation, edit locking, comments and admin list settings. Existing collections also expose title/date field selection and comment moderation, close-after-days and signed-in auto-approval. The source creation interface does not accept moderation/title/date settings; those are edited after creation. Choosing default creation settings omits advanced metadata, retaining source defaults and SEO derivation. Explicit settings preserve empty/false values.

Add-field forms expose the source's 17 types and required/unique/indexed/searchable/translatable flags, widget name, typed JSON defaults, validation and options. Existing field forms retain label/scalar options and add native keep/set selectors for the complete stored metadata. All form instances use their own pending state. The supported type changes remain exactly `string`/`text`/`slug` aliases; matching SQL affinity alone does not authorize other type changes. Changing required/unique or making an existing translatable field non-translatable retains the pinned migration error. Defaults and validation change metadata without rewriting existing content.

JSON editors provide the persisted typed settings while dedicated rich field builders, block-type administration, relation/media lifecycle integration, FTS and development type generation remain unfinished. Accepting a blocks/reference/media descriptor or storing a searchable flag does not implement those subsystems. Their omitted source assertions receive no credit.

Collection/field reordering uses JSON slug arrays in native registered forms. The server checks trusted schema-manager permission before parsing domain inputs, then the existing configuration/mutation gate. Collection metadata and destructive/reorder operations retain native collection version/timestamp preconditions; field addition retains schema-version preconditions. Field metadata edits retain pinned last-writer-wins behavior. The new form instance identifiers must match their collection/field and are removed before service calls. Successful collection deletion redirects to the parameter-aware schema list for both native and enhanced submissions.

Pinned `registry.ts:1835–1855` field reordering loops through the supplied slugs: partial lists leave omitted sort orders intact, duplicates update the same field again, and unknown valid slugs affect zero rows. It does not advance collection version/timestamp. The complete immutable source probe and compiled native Node/D1 assertions reproduce `['two']`, `['one','one']`, and `['missing']` with those exact outcomes. Native collection preconditions fence concurrent collection metadata changes but do not turn field ordering into revision-consuming optimistic concurrency; another order from the same metadata snapshot remains accepted. Native atomic batches and identifier validation remain documented local substitutions. No complete-permutation rule or metadata advancement is claimed or added; type-generation notification remains incomplete.

Collection ordering validates every native collection snapshot within the same atomic batch. Each SQL guard statement now binds at most four values, avoiding D1's per-statement bind limit while retaining the count fence, mandatory snapshots, order writes and guard cleanup in one transaction. The test-first 34/100-collection checks and injected middle/last snapshot races verify Node/workerd D1 success or complete rollback with empty guard storage.

## Deletion behavior

Pinned `registry.ts:1185` guards active content unless `force` is true, then runs the media activation fence and FTS cleanup before dropping the content table and registration. The current port implements the content/force guard, physical field/collection removal and registry cleanup; activated media deletion, FTS cleanup, relation cascades, cache invalidation and type-generation notification remain incomplete. No arbitrary guard against unrelated operator foreign keys is added.

The [immutable source probe](../scripts/reproduce-schema-administration-source.mjs) loads the **complete, unchanged registry** and real source transaction/dialect helpers from the pin. Inactive media, FTS, cache and development-type fixtures are explicit substitutions; the first probe attempt stopped in an unimplemented capture fixture, then the corrected inactive capture fixture reached both assertions. It adds zero copied declarations or subsystem parity credit. With SQLite foreign keys enabled, a forced drop cascades external `ON DELETE CASCADE` child rows; `RESTRICT` throws and retains parent/child rows and registration. Local Node and real workerd D1 preserve those outcomes. The pinned behavior is retained rather than silently changed.

A supplemental legacy-reference fixture proves deletion also removes a retained physical column before its slug is reused. Native CAS and adapter-proven atomic rollback remain local substitutions; a test-first race repairs the error code for a metadata change between selection and deletion. It now reports `CONFLICT` rather than incorrectly reporting `COLLECTION_NOT_EMPTY` and leaves schema, rows and guard storage intact. It does not change source foreign-key errors.
