# Bounded trusted-binding D1 adapter

Landed in [PR #10](https://github.com/sveltery/cms/pull/10) at merge `30ba4831cd8f402541a46161a151271fa650b213`. Landed state does not establish specific acceptance of the documented deviations. The compatibility register uses C-23 for the D1 seam, C-17 for result/parameter metadata and C-18 for migration races; C-16 belongs to scalar preview.

`openD1(binding)` in [d1.ts](../src/lib/server/database/d1.ts) accepts an operator-supplied **raw D1Database binding**, returns the existing `CmsDatabase` seam, and does no resource lookup, provisioning or migration. The caller owns the binding/runtime lifetime. `close()` destroys Kysely; it does not dispose the binding. Call `migrateCms` explicitly before composing the existing CMS service. No production hook/factory, login, account setup, credentials, hosting configuration or enabled UI writes are added. The server mutation gate remains default-disabled.

## Behavior and bounds

Kysely 0.29.2 supplies the SQLite compiler. A small structural driver uses `prepare(sql).bind(...parameters).all()` for ordinary queries. The raw-binding adapter reports `supportsMultipleConnections: true`, matching upstream: a pending read cannot hold Kysely's SQLite mutex over other independent subrequests. The structural type cannot verify whether a caller supplies a session-shaped wrapper; callers must supply the trusted raw binding. D1 sessions, bookmarks, request coalescing and read replication are outside this contract. Mock overlap/liveness tests demonstrate the Kysely mutex behavior; they do not prove workerd cancellation recovery under a disconnected HTTP request.

Every `atomicBatch` prepares all compiled statements and invokes **exactly one binding.batch**. No per-statement execution fallback or callback transaction emulation exists. Real local D1 tests fail batches after DML and CREATE/ALTER/DROP DDL, then prove all application objects and rows are unchanged. Migration failure tests cover both fresh and exact v1 fixture upgrades, failure after auth DDL and failure at the v2 marker, followed by successful retry. [Cloudflare's binding documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/) specifies batch rollback on failure; the executable evidence here is local Miniflare/workerd, not a live D1 service.

Upstream declares a compound-SELECT ceiling of five on its adapter. The selected declaration assertion is retained. CMS queries do not use compound-SELECT splitting; this slice does not port EmDash's splitter or establish a live service limit. Callback transactions, streaming, generic introspection and Kysely migration-lock APIs reject explicitly. Upstream's wider introspector/row-lock machinery is unimplemented; this CMS uses its existing bounded schema probe and atomic migrations, not the general EmDash migration runner.

The result mapper preserves upstream `rows` (including DELETE RETURNING), `insertId`, and **undefined for zero `numAffectedRows`**; positive changes become bigint. The upstream kysely-d1 0.4.0 ordinary-query driver additionally exposes deprecated `numUpdatedOrDeletedRows`; its batch mapper omits that alias. This bounded adapter omits the alias on both paths, following the existing Kysely 0.29.2 QueryResult seam, which no longer declares it; CMS code does not consume it. Local/upstream probes assert this key-presence difference. Node's non-returning driver instead supplies `0n` for zero changes, and its RETURNING path exposes rows without affected-count metadata. CMS CAS tests depend on returned rows and guards, not on equal result metadata. These API/runtime differences are documented without metadata parity credit or a specific acceptance decision.

Parameters are forwarded unchanged, matching the pinned D1 implementation. Real local D1 accepts null, strings, numbers, booleans as 0/1, Uint8Array, ArrayBuffer and byte-number arrays (BLOBs return number arrays). It rejects undefined, bigint, objects, Date and boxed numbers before batch execution; a valid preceding statement therefore does not commit. Node normalizes undefined to null and supports bigint/Uint8Array, rejects ordinary arrays and ArrayBuffer, and returns BLOBs as Uint8Array. These low-level variants are **not cross-runtime parity**; the bounded CMS persists validated string/null data and numeric markers. Other typed arrays, non-finite numbers, unsafe integers, out-of-range byte arrays and large payload/statement limits remain untested.

Local D1 initializes its platform-owned `_cf_METADATA` table on the first write, even when the user batch fails. The pinned upstream adapter produces the same result. Rollback comparisons exclude exactly that internal table and compare every application object. No CMS DDL or migration marker survives a failed batch. This bookkeeping is a measured local runtime difference from Node, not a CMS repair or an upstream bug claim.

## Migration and session evidence

The previous Node-only equality checks missed D1's envelopes. [errors.ts](../src/lib/server/database/errors.ts) removes only the measured anchored `D1_ERROR: … [at offset N]: SQLITE_ERROR/SQLITE_CONSTRAINT` envelope for classification; the original error is retained. Fresh migration races must match exactly `table _cms_migrations already exists`; v1 upgrades exactly `CHECK constraint failed: pass = 1`. Recovery still requires a complete committed v2 schema. Deterministic barriers force two adapters through preflight before their actual batches; both callers succeed after one real D1 batch failure. A concurrent upgrade between preflight reads succeeds. Unrelated failures propagate even if v2 is complete. Concurrent registered-slug creation likewise maps only the exact unique-column failure to COLLECTION_EXISTS. Unknown envelope formats remain unexpected errors. No retry for arbitrary I/O failures or interrupted requests is implemented.

The [shared storage contract](../tests/helpers/storage-contract.ts) executes on Node SQLite, a real local D1 binding proxy and inside workerd with **no nodejs_compat**. It verifies empty fresh/idempotent auth migration; persisted scalar schema; escaped literal defaults, NUL and own-key data; required/unique constraints; draft and schema CAS; partial update; retained soft deletion; and joined persisted session reads with current role, disabled status, exact expiry and revocation. Separate tests prove v1 content/schema preservation and file-backed session revocation across runtime dispose/reopen on both Node and D1. Test accounts/sessions are inserted only in fixtures; product APIs cannot provision them.
