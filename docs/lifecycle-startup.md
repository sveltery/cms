# Canonical lifecycle startup

This slice registers content lifecycle provider **5** with `migrateCms`. Fresh startup installs `_cms_revisions`, `_cms_revision_prune_queue` and their two indexes. New collections retain the existing system columns, allow general text status values with the `draft` default, and include nullable `primary_byline_id`. It prepares storage for the separately owned lifecycle services; it does not introduce publishing remotes, admin controls or a scheduler.

## Known-layout upgrade

Before writing, the provider independently enumerates registered collections and checks their tables. Required local system definitions, the slug/locale constraint, metadata field names and physical column types must match supported layouts. Missing tables, views, unregistered content tables/columns, incompatible system definitions, temporary objects and partially installed lifecycle tables reject with `MIGRATION_REQUIRED`. Latest provider validation also checks all four static lifecycle objects and validates known metadata/auth descriptors before reading dynamic content metadata.

Every startup write batch begins with a read-only guard over the exact previously validated static table/index DDL and sorted migration markers. It also requires future static names and intermediate rebuild names to remain absent. Provider version-zero descriptors declare those static names without reading missing metadata. This guard runs before foundation/tracking writes on a fresh database and before intentional v3/v4 upgrades of historical DDL, so the old validated layout is checked before the migration itself changes it. The same guard precedes latest-v5 trash-index backfills; an exact concurrent winner is accepted only after complete latest-layout and index revalidation. Auth profile/role/session values and unrelated operator tables/data are excluded. Preflight continues using the existing SQL normalization; a concurrent rewrite of equivalent stored DDL can conservatively abort the current attempt and pass on retry.

Fresh preparation also scans content objects before metadata exists. An orphan `ec_*` table or view rejects without installing foundation tables or migration markers. An empty metadata/content snapshot remains guarded inside the same transaction after foundation DDL; an orphan committed after preflight causes complete installation rollback and `MIGRATION_REQUIRED`, preserving the other writer's object and rows. Repeated startup still rejects that untouched unsupported layout.

The upgrade removes only the historical `CHECK(status = 'draft')` and adds nullable `primary_byline_id`. It copies every existing column explicitly into a replacement table and restores the original SQL for indexes and triggers in the same adapter-proven atomic batch. When any table needs rebuilding, all triggers attached to registered content tables are removed after the transaction snapshot guard, including triggers attached to a table that needs no rebuild. Indexes are restored with their own table; original trigger SQL is restored only after every content table exists. This preserves forward/reverse cross-collection and self-references, and copied rows do not fire attached triggers during installation. Unrelated operator triggers are left intact. Existing IDs, content, locale, timestamps, numeric version, revision pointers, field defaults, NULL values, unique enforcement, metadata and authentication rows remain intact. A transaction-local snapshot guard covers registered schema versions/fields, content DDL/indexes/triggers and operator tables referencing content, preventing a preflight race from overwriting a new schema write. Failed batches roll back provider objects, rebuilt tables, rows, guards and version markers. A stale startup caller accepts a winner only after validating a complete latest layout.

Operator-created inbound content FKs or unrecognized field constraints reject before rebuilding, because SQLite dropping a referenced parent can activate cascading actions. The provider preserves supported registry metadata/auth FKs; it does not repair an arbitrary operator database. All validation uses disposable local fixtures and opens no operator database.

Reserved content namespace detection follows SQLite's case-insensitive ASCII identifiers, including `EC_*` tables/views/indexes and their preflight races. Tables, views and indexes share that namespace; trigger names occupy a separate namespace and may equal an existing or future content table name. Content table lookup and attached index/trigger owner comparisons use the appropriate object type and folded owner name, preserving differently cased trigger declarations. Every field metadata row must reference a registered collection before any per-collection physical validation; an orphan row is rejected rather than silently omitted. Latest-v5 startup also validates and guards this same complete snapshot around a missing trash-index backfill, so namespace/field writers cannot bypass validation on that remaining write path. External FK classification reads the identifier immediately after an actual `REFERENCES` token, accepting SQLite quoted targets and skipping comments and ordinary string literals. An unrelated operator FK to `operator_users` or `_cms_auth_users` remains supported even with an `ec_note` column or content-like text in comments/defaults, including an operator-owned FK violation. Its original DDL and rows are retained; no blanket database-wide `foreign_key_check` is used. Candidate FK-table DDL stays in the transaction snapshot so an actual content-reference writer cannot bypass the guard; a concurrent unrelated candidate-schema edit can conservatively abort that attempt, then pass unchanged on retry.

External views and triggers on unrelated tables are also checked for content table references before rebuilding. Quoted/schema-qualified targets, joins, parenthesized table groups, nested CTE queries and trigger read/write statements receive the same `MIGRATION_REQUIRED` rejection without writes. A CTE name that shadows a content table, ordinary content-like column names, literal contents and comments are not table dependencies. Unrelated operator views/triggers retain their original SQL and rows. All view/trigger DDL is included in the atomic snapshot: a dependency created after preflight rolls back every migration object and marker, preserving the other writer's object and data. An unrelated concurrent view/trigger edit can conservatively abort that attempt and be accepted on retry. This remains a local strict known-layout adaptation, with no copied-source assertion credit.

SF-02 physical field defaults/indexes and inherited scalar uniqueness [issue #20](https://github.com/sveltery/cms/issues/20) remain separate. This upgrade performs no general default/index/uniqueness reconciliation. Historical stricter local system NOT NULL/version/slug constraints and missing revision-pointer FKs remain as recorded local storage differences. The source queue migration's retry/backfill assertion, other system tables, PostgreSQL/libSQL and deployed D1 are unported here. Specific acceptance of the local migration/atomicity substitutions is not recorded.
