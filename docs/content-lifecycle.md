A read-only service audit identified a host integration error in mixed saves: `{data, slug, publishedAt}` staged the new slug but also copied it into the live row during the metadata update. Pinned runtime blob `055ed1307ba4029e120cad989bc9b0e8c2d72afe` at lines 3887–3891 passes an undefined slug when draft revisions are used. The host now does the same. The saved draft retains its new slug, while the live slug changes only at publication. This fidelity repair is covered by two original Node/local D1 regressions, with zero new source declaration credit.

The same audit found that native revision restore checked the caller's token, then let the source repository take a newer baseline after a concurrent save. Native restore now passes its authorized read token to optional repository preconditions: each restore method checks that token after its own read and uses it in the atomic SQL predicate. Omitting the new argument preserves the source method's behavior. This is an intentional stronger native concurrency contract, recorded as LC-02 in the [compatibility register](../parity/emdash/compatibility.md), rather than a verified upstream bug fix. Both revision-enabled and plain collections have Node/local D1 regressions for saves before and after repository refetch.
