# Bounded schema administration

The current [persisted schema domain](full-schema.md) supports all 17 pinned field types, richer metadata, index flags and deletion/reordering APIs. The [expanded administration controls](schema-administration.md) now expose all 17 persisted types, collection/field settings, ordering and deletion. Dedicated field builders and the block/media/relation/FTS/type-generation subsystems remain unfinished. The rest of this page records the historical bounded checkpoint. Version 3 upgrades existing metadata and preserves physical content definitions and values; version 4 registers empty identity tables. The evidence and compatibility records below describe the historical bounded administration checkpoint unless a later subsection explicitly supersedes it.

## Native inputs and concurrency

The components spread the registered form directly onto `<form>` and each native descriptor directly onto its input/select/textarea through `field.as(...)`. Collection detail forms use `.for(collectionSlug)` to isolate their state. Kit injects its native instance `id`; the form validates that it matches `collection`, then removes it before the service call. Bare registered requests may omit this framework key. Kit 2.70.3 injects the instance `id` into native/enhanced submission data; a bounded optional `id` must equal the collection slug and is stripped before the domain service. The list embeds creation instead of a separate upstream `/content-types/new` route. Validation issues render inline; domain failures use the nearest Kit error page instead of React toast callbacks. Creation success remains on the list with a receipt and refreshed query; upstream navigates to its new detail. Local controls do not reproduce upstream automatic slug/plural-label generation, the React dialogs, full dirty tracking, tabs or localization.

Collection metadata and additive-field controls below retain their separate encoding and creation bounds; the later field-options form has explicit keep/set/validation-clear modes documented in the extension. Creation defaults omitted `supports` to `['drafts', 'revisions']`; explicit JSON-string `[]` stores no flags. Updates omit supports to retain them and send `[]` to clear them. Disabled optional singular-label/description/default controls produce absent keys; an enabled empty description/default sends `''`. Singular labels retain the existing nonempty trimmed label rule. The UI supports toggles serialize flags in draft/revision order; the remote preserves the supplied supported-array order. Null metadata/defaults are unsupported. The native supports wire value is a bounded JSON string, not an upstream JSON array. Unknown client properties, including principal/role claims and content `_rev`, reject; the validated framework instance `id` is the sole transport-only accepted key.

Metadata forms transport canonical decimal `version` plus `updatedAt`, converting to the landed service's required **`{ version, updatedAt }` CAS**. Metadata writes do not increment schema version. Additive fields transport canonical decimal `expectedSchemaVersion`, converting to the existing field service's schema-version CAS; successful addition increments schema version. Content `_rev` applies to content editing and is not used here. These are existing CMS concurrency guarantees, not preconditions supplied by the pinned EmDash schema requests.

Only `slug`, `label`, `type: 'string' | 'text'`, native required/unique checkboxes, optional string default, and optional minimum/maximum lengths are exposed for addition. Empty length controls mean omitted bounds; canonical decimal lengths convert to safe integers and are revalidated by the domain service. Effective minimum/maximum/default-length conflicts produce native issues before the handler; the domain checks them again. Existing limits remain: identifier 63 characters, trimmed label 200, description 2,000, collection capacity 100, field capacity 32, string default maximum 100,000; the existing string value default bound is 200 and text bound is 100,000. Unsupported flags/types/properties earn no source credit.

## Future scalar-field fidelity repair

The [bounded scalar repair](scalar-field-fidelity.md), proposed in [PR #21](https://github.com/sveltery/cms/pull/21) after trash/restore integration, follows EmDash 1.1.0 immutable `913cb1bb9b7f08c3ff0d258b4420e53835b6a58e`. New required string/text columns get `NOT NULL DEFAULT <explicit default or ''>`; implicit empty SQL defaults do not become field metadata. New optional defaults are metadata only, with omitted raw/content inserts yielding SQL NULL. New `unique: true` remains metadata only with no field-specific SQL index or full/partial content uniqueness enforcement. [Issue #20](https://github.com/sveltery/cms/issues/20) defers that verified inherited bug; it is deliberately preserved.

Existing tables remain divergent pending a separately reviewed upgrade. No existing column default/index or stored value is rewritten, and no existing database is migrated by this repair. [Paired original supplemental probes](../tests/scalar-field-fidelity.test.ts) and the [complete immutable upstream reproducer](../scripts/reproduce-scalar-field-upstream.mjs) cover 24 cases per Node/local D1 runtime, raw omissions, explicit NULL, duplicates, full/partial validation, and persisted restart. Local schema authorization/CAS and independent DDL/DML rollback remain covered. These probes add no copied-source declaration credit or deployed parity.

The historical required-empty-string difference (SF-03) is covered by the separate [required scalar validation repair](required-scalar-validation.md): explicitly supplied required `''` rejects in full/partial mode regardless of metadata default or absent/zero/cleared minimum. Whitespace and omission/default behavior stay unchanged; partial updates preserve untouched legacy empty/null values, which remain readable through trash/restore/reopen. That repair changes no physical definitions or metadata and grants no new complete source-declaration credit. Upstream D1 transaction fallback and local adapter-proven atomic batches remain the separate C-07/SA-03 difference, with specific acceptance unrecorded. The validation repair's final-head bootstrap, secured browser, review and CI evidence remains separate from the physical repair's historical runs.

## Existing scalar field labels

The [bounded label editor](field-label.md) adds `updateSchemaFieldLabel` and one native ``.for(`${collection}/${field}`)`` form per existing string/text field, with direct form/descriptor spreads and validated, stripped framework `id`. Exact nonempty label strings remain untrimmed and unbounded; other edit properties reject. No precondition, collection timestamp/version change, physical schema/index/default change or content rewrite occurs. Same-field writes are last-writer-wins. Collection metadata forms cannot overwrite labels; their existing tokens remain valid without certifying freshness of the fields display. The label-only subset of registry.test.ts:668 is one partial assertion, zero complete declarations; the existing 11 declarations/25 assertions remain separately counted. FL-01–FL-03 record native/strict transport, trusted gate/error order and atomic receipt/subsystem differences. Run evidence and merge gates are recorded in the feature ledger.

The [field metadata source ledger](field-edit-ports.json) separately adds registry.test.ts:668 sort-order coverage while retaining its omitted widget expression, plus both direct-registry concurrent-edit expectations from MCP schema.test.ts:1003 with adapted setup. Prior schema-admin and label-only counts/evidence above remain historical and unchanged; MCP schema.test.ts:982 contributes supplemental validation observations only. No whole-family/REST/React/MCP parity is inferred.

The landed [pattern-validation extension](pattern-validation.md) adds scalar pattern controls through the existing additive-field and field-options native forms. [Native implementation and check evidence](pattern-validation-native.md) supersede the historical length-only validation surface at merged main `b54560671483162b4584d05599b482572fe781bb`. Existing collection/field concurrency, capability disclosure, default-disabled writes and broader unsupported schema properties remain as documented above; the extension adds no new schema remote export or content-editing activation.

Native `patternMode` accepts `omit`/`set`, defaulting to `omit`; the source control is `pattern`. Creation starts at omit; set requires a string, accepts `''` and reports malformed JavaScript syntax at the pattern field. Omit ignores even a malformed submitted source, and both transport keys are stripped before the service call. Existing field-options patterns participate only in `validationMode: set`: keep omits the whole validation property, clear supplies `null`, and set replaces it with populated length bounds plus pattern only when its mode is set. A stored empty pattern initializes set so it remains distinct from an absent source. No regex attribute is added to disabled content controls; these schema controls configure JavaScript server validation rather than HTML's different pattern matching semantics.

The source control is a textarea. Existing options submit a JSON-string `patternOriginal`; when normalized submitted textarea text equals normalized original text, replacement preserves the exact original source, including LF/CRLF/lone-CR distinctions. Changed sources and creation save the actual submitted value: native browsers normalize textarea line breaks to CRLF, while enhanced requests preserve their submitted string. This does not promise preservation of authored creation bytes. Keep/clear modes ignore the JSON value; malformed selected JSON or an invalid decoded pattern produces a pattern-field issue. The validated transport snapshot is removed before the domain service call.
