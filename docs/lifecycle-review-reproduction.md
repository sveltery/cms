## Observed source behavior

On the original runtime, a published revision entry saved directly with `{data:{title:"Rejected draft"},publishedAt:"not-a-date"}` returns `VALIDATION_ERROR`, but retains the newly staged draft pointer, its data and a version increment. Live title and publication date stay unchanged. Calling the complete API update handler with only that invalid metadata leaves the entire row unchanged: its transaction starts after the runtime has staged the draft. The complete public PUT with that invalid date returns 400 before any write; its original decoder requires ISO datetimes. The direct-runtime invalid date is not a public partial-write reproducer.

The actual public reproducer uses accepted input `{data:{title:"Accepted REST draft"},publishedAt:"2020-01-01T00:00:00.000Z"}`. A real SQLite `BEFORE UPDATE OF published_at` trigger aborts only the metadata write for that date; draft staging does not touch that column. The original PUT callback with an actual `Request` accepts the ISO value, passes original admin/ownership gates and returns 500 `CONTENT_UPDATE_ERROR`. The draft pointer/data remain persisted and version increments; live title/date stay unchanged.
