## Request and content behavior

| Pinned source | Observable contract |
| --- | --- |
| [Request field validation](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/api/schemas/schema.ts#L97) | Create/update accepts an optional string `validation.pattern`, including `''`, whitespace, slash-looking strings and long sources. It does not trim, parse delimiters/flags or cap length. Defined values must compile with `RegExp(pattern)`; malformed syntax produces the custom issue at `validation.pattern`, message `Invalid validation pattern`. Non-string values, including pattern `null`, fail. The containing validation object may be omitted, `null`, or `{}`. Unknown request keys are stripped upstream. |
| [Field update replacement](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/schema/registry.ts#L1454) | Supplied validation replaces the whole object. Omission/undefined preserves it; pattern-only edits remove prior length rules and length-only edits remove prior pattern. `null` stores SQL NULL, projected upstream as undefined; `{}` stores JSON `{}`. Empty pattern stores a real `"pattern":""` property. Scalar metadata edits leave columns, indexes, existing content and collection rows/timestamps unchanged. |
| [Generated string validation](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/schema/zod-generator.ts#L256) | Truthy pattern compiles with `new RegExp(pattern)` without flags. Matching uses JavaScript substring semantics unless the supplied source anchors it. Matching is case-sensitive and uses UTF-16 units without `u`. A slash-looking source such as `/a/i` matches literal slashes and text; it does not enable `i`. `''` disables pattern enforcement. Length and pattern checks compose independently. |
| [Content validator](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/api/handlers/validation.ts#L149) | Full and partial validation check supplied string/text values. Optional omission, undefined and null bypass pattern. Partial omission of required fields passes. Required empty string retains the separate required-empty failure. Pattern rejection produces `invalid_format` with `format: 'regex'`; the reference message includes the compiled expression. |
| [Default wrapper](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/schema/zod-generator.ts#L65) | An omitted configured default bypasses validation, including pattern mismatch. The content validator returns only `{ok:true}` and leaves caller input unchanged. It does not materialize parsed defaults into storage input or alter physical SQL defaults. Explicitly supplied mismatching default text still fails. |

The registry's direct create/update API does not validate pattern syntax. A malformed pattern can therefore be persisted by bypassing the request schema. Reads and unrelated metadata edits retain it; the generated schema eagerly compiles it and throws `SyntaxError` before parsing either full or partial data, including absent/null values. P14/P15 reproduce this inherited behavior. The coordinated local shared registry/domain syntax guard is a stricter boundary, proposed for integration record PV-01 rather than credited as upstream parity. Existing malformed metadata must preserve eager validation failure unless a separate fidelity decision changes that contract.

The pinned [admin FieldEditor](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/admin/src/components/FieldEditor.tsx#L885) exposes `Pattern (Regex)`, initializes missing pattern as `''`, and only includes a truthy pattern in the replacement validation object. Source inspection does not establish rendered React behavior. Native SvelteKit keep/set/clear modes, explicit saved empty pattern, multiline controls, errors/receipts and refreshes are separate transport/presentation adaptations proposed for integration record PV-03. Proposed integration record PV-02 retains the existing scalar content/metadata boundary differences, including local SQL-NULL projection and bounded content sizes. PV-01–PV-03 are proposed identifiers in this source ledger; the current canonical core records are PV-CORE-01 and PV-CORE-02. The canonical [compatibility register](../parity/emdash/compatibility.md) owns decision and landing status; neither this reference run nor a merge accepts those differences.
