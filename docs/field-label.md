## Preserved label behavior

Only the label of an existing `string` or `text` field can change. Collection and field slugs identify the target; its slug, type, required/unique flags, default, validation, order and every other stored attribute remain intact. A label must be a string with at least one character. It is **not trimmed** and has **no 200-character maximum**: whitespace-only labels and longer labels retain their exact submitted value. This follows the pinned [request schema at lines 232–234](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/api/schemas/schema.ts#L232). Creation and collection metadata retain their existing, separate trimmed/bounded label validation.

The pinned [registry operation](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/schema/registry.ts#L1416) takes no request precondition. Its label assignment at [line 1542](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/schema/registry.ts#L1542) changes field metadata without touching the collection timestamp. The local operation preserves this: no expected-label, version, timestamp or content `_rev` is required or accepted. Same-field edits are last-writer-wins; resubmitting the same label succeeds. Label writes change neither collection schema version nor collection `updatedAt`.

Collection metadata updates cannot write field labels. A label edit therefore leaves an existing metadata form's `{ version, updatedAt }` tokens valid; those tokens protect the metadata operation and do **not** certify freshness of the entire displayed fields list. Additive-field schema-version tokens also remain valid after a label edit. Addition still increments schema version under its existing CAS; metadata changes still follow their existing timestamp/version contract. Independent operations preserve each other's values.

The operation performs no migration, physical-column alteration, default/index repair or content/value rewrite. Existing legacy physical defaults and scalar unique indexes remain divergent exactly as described in [scalar-field fidelity](scalar-field-fidelity.md). Editing a label cannot upgrade those layouts. Content values and revision tokens remain unchanged.

## Trusted boundary and native editor

`cmsService.updateFieldLabel({ collection, field, label })` delegates to `SchemaRegistry.updateFieldLabel(collection, field, { label })`. The service requires a trusted `schema:manage` principal before parsing or accessing storage. The registered mutation also passes the existing server-derived mutation gate; production writes remain default-disabled. Client role, principal and capability properties confer no authority. Domain and remote inputs are strict: broader field-edit properties, including type, slug, required, unique, default, validation, widget and sort order, reject instead of being silently ignored. An existing collection/field pair determines the persisted target identity. After reading target identity, one `UPDATE … RETURNING` checks the field ID, collection ID, field slug and continued collection ID/slug existence. No label/timestamp/version guard is added. A disappeared or replaced target reports `NOT_FOUND`. The database returns the atomic update's row, so a subsequent writer cannot alter this operation's receipt.

Each field has one native SvelteKit remote-form instance. The component spreads the registered form directly onto `<form>` and each `field.as(...)` descriptor directly onto its native input. Hidden collection/field descriptors receive explicit values. Kit 2.70.3's ``.for(`${collection}/${field}`)`` instance key is transport data: the optional injected `id` must match the collection/field pair and is stripped before the service call. Bare registered submissions may omit it. Each instance owns its pending state, validation issues and result; capability-disabled controls stay disabled. Successful mutations refresh the schema list/detail, content collection list/detail and editor manifest through the existing query refresh helper.

Pinned [FieldEditor lines 485–492](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/admin/src/components/FieldEditor.tsx#L485) regenerates slugs only for new fields. Its [label and slug controls at lines 808–823](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/admin/src/components/FieldEditor.tsx#L808) allow an existing label to change while disabling its slug. The local scalar editor preserves that distinction. React dialogs, localization, type selection and the broader field builder remain incomplete scope.
