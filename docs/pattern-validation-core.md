# Scalar pattern validation core

This focused server/storage milestone starts from CMS main `9e0cf4e`, against EmDash 1.1.0 immutable pin [`913cb1bb9b7f08c3ff0d258b4420e53835b6a58e`](https://github.com/emdash-cms/emdash/commit/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e). Preserve [MIT attribution](../notices/emdash-MIT.txt). The [canonical compatibility register](../parity/emdash/compatibility.md) owns inherited differences and integration evidence.

The string/text [creation schema](../src/lib/server/database/validation.ts) and [metadata-edit schema](../src/lib/server/database/field-edit-validation.ts) accept `validation.pattern` as an unchanged JavaScript regular-expression source. Empty, whitespace and slash-looking strings are valid when `new RegExp(source)` compiles; no flags, trimming, implicit anchors or slash parsing are added. Invalid syntax produces `Invalid validation pattern` at the pattern property. Null and other non-string pattern values fail. Metadata defaults are not pattern-checked. Omission preserves metadata; editing validation replaces the whole object, null clears it and `{}` remains distinct.

At every full or partial content write, [entries.ts](../src/lib/server/database/entries.ts) eagerly compiles every truthy persisted pattern before checking supplied fields, following pinned [zod-generator.ts:256](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/schema/zod-generator.ts#L256) and [validation.ts:199](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/core/src/api/handlers/validation.ts#L199). Supplied strings, including optional empty strings, must match. Empty pattern source disables matching. Optional null/omission and omitted metadata defaults retain existing behavior without default materialization. Required empty rejection and length bounds remain effective. An invalid legacy truthy pattern throws `SyntaxError` even when its field is absent, null or untouched. Reads, manifest projection and trash/restore still expose retained legacy content. The [manifest](../src/lib/server/content/manifest.ts) projects the stored source unchanged, including empty or legacy invalid source, and excludes unrelated validation properties.

No migration, physical-default/index change or content rewrite is included. Pattern metadata updates leave collection timestamps/version, content rows and entry revision tokens unchanged. Rejected input attempts no mutation or atomic batch. Existing local bounds remain: strict supported keys, generic `CmsError` rather than complete Zod issue details, SQL NULL validation projecting as null, nonnullable creation validation and the inherited creation-schema acceptance of an empty validation array as `{}`. The latter predates this milestone and differs from pinned Zod; metadata edits already reject arrays. Low-level pinned registry methods accept malformed regex metadata, whereas the local registry continues applying its existing request-validation boundary. This does not claim static field-factory, URL field, MCP, generated-Zod, deployed-hosting or whole-product parity.
