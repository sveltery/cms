# Schema form choices during pending responses

This native Kit repair in proposed [PR #37](https://github.com/sveltery/cms/pull/37) prevents a completed schema submission from discarding the user's next selection. EmDash 1.1.0 at immutable [`913cb1bb9b7f08c3ff0d258b4420e53835b6a58e`](https://github.com/emdash-cms/emdash/commit/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e) remains the product behavior authority. Its [FieldEditor](https://github.com/emdash-cms/emdash/blob/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e/packages/admin/src/components/FieldEditor.tsx#L885) uses controlled React inputs. The observed reset race belongs to the local native framework adaptation; this repair earns zero upstream declarations or assertion expressions. Preserve the [upstream MIT notice](../notices/emdash-MIT.txt) and the existing [native pattern contract](pattern-validation-native.md).

Kit 2.70.3's default remote form enhancement awaits submission and a rendering tick, then resets the HTML form. Its pending count spans that entire operation. Previously only submit buttons were disabled while pending. A user could select **Clear validation** after the previous replacement reached storage but before its reply arrived; that previous successful form reset silently returned the selection to **Keep validation**. Submitting again retained `{}` instead of clearing validation to `null`. The failure trace from [CI 37059828464](https://github.com/sveltery/cms/actions/runs/37059828464), job `111013471736`, shows Clear selected at `47091.247ms` and Keep restored at `47095.662ms` before the next submission.

Each existing schema form now disables its own fieldset while its own remote instance is pending: field options, field label, collection metadata, add field and create collection. The trusted disabled gate remains part of the same expression. Other form instances remain usable, and controls become available after the previous submission's refresh/reset finishes. Ordinary native submissions retain their server validation and authorization. This guard applies to these explicit metadata submissions; future content autosave needs independent dirty-snapshot preservation and is outside this repair.

`tests/browser/pattern-pending.spec.ts` was committed before the product change. Its primary case executes the actual registered mutation with `route.fetch()`, holds the reply after the database write, begins the next Clear selection and releases the response without a timing sleep. The expected final stored value remains `null`. On test-only published head `2d0af46a817fdec27763a05dc7da92361c1a321f`, [CI 37061070739](https://github.com/sveltery/cms/actions/runs/37061070739), secured browser job `111017564349`, failed that exact assertion with **Received: {}**, while all 48 existing browser cases passed; validation also passed. Four additional per-instance held-response checks for metadata, label, add and create were committed at local `63dee18` before the five-line product repair at local `c8ab6ab`. These supplemental checks verify that the submitted form's fieldset is disabled while another available form remains enabled, then returns to enabled after completion. They do not claim upstream test-first evidence.

Local checker and final bootstrap results, secured default/Node browser green evidence, exact-head independent review, approval and landing are recorded separately in PR #37. Browser sandbox and host/network policy remain unchanged. Specific acceptance of the native pending-control adaptation is not recorded; implementation approval and source parity are distinct. The [compatibility register](../parity/emdash/compatibility.md) preserves the remaining native transport differences and feature limits.
