# Typed native content and public validation issues

Proposed native transport feature on [schema PR #39](https://github.com/sveltery/cms/pull/39), pinned to EmDash 1.1.0 [`913cb1bb9b7f08c3ff0d258b4420e53835b6a58e`](https://github.com/emdash-cms/emdash/commit/913cb1bb9b7f08c3ff0d258b4420e53835b6a58e). The shared schema validator, generic storage codec and migrations belong to that dependency. This feature has no migration, production activation or deployment.

Create/update retain collection, ID, locale, slug and mandatory update `_rev`. `data` accepts a JSON document or enhanced JSON record. Native controls use `data.<field>`, `n:data.<field>` and `b:data.<field>` for simple values; `jsonData.<field>` carries complex JSON text. Per-field JSON is parsed, merged and removed before the service; duplicate representations reject. The shared guard bounds the merged record to 32 identifier keys and 200,000 serialized characters. Ordinary nested string controls retain the 100,000-character limit and field error path. Syntax errors identify the JSON control; structural framework errors remain Kit form issues.

Kit's static form types cannot express dynamic JSON/nulls and interpret nested boolean arrays as required checkbox schemas. Only this dynamic input adapter uses `Record<string, any>`; actual runtime validation is mandatory and domain output remains `Record<string, unknown>`. No unchecked handler is introduced.

Trusted domain validation errors now return native status 400, `VALIDATION_ERROR`, the exact source field/message summary and `details.issues`. Count/order, dotted paths, required/unknown/reference codes, bounds and formats are retained. Only path/code/message/origin/minimum/maximum/format cross the boundary; exception inputs, SQL and stacks do not. Other errors keep existing sanitized envelopes. Current persisted identity, permissions and ownership precede domain validation. Malformed legacy truthy patterns still throw eagerly; Kit conceals the exception and no write occurs.

The manifest maps all 17 types: legacy `text` remains string-backed `richText`, distinct from array-backed `portableText`. Integer/number and slug/string keep source kind aliases; an additional native `type` distinguishes them. Fields expose widgets, options, translatable metadata and every declared pinned validation key. Legacy enum choices override widget options with source-capitalized labels. Defaults remain omitted. Unknown types and unsupported repeater subtypes expose unsupported descriptors. Collections expose supported supports/sidebar/routing/SEO/list metadata; list columns deduplicate, reject missing/unsupported fields and cap at four with the pinned warnings.

Least disclosure is an intentional difference: upstream spreads arbitrary raw validation keys; this projection omits undeclared keys, including nested repeater metadata. Open supported widget options remain public. Storage columns/defaults/content/admin internals remain omitted. Existing 100-collection/32-field limits, 50-ID batching, ordering, inherited-name omission and propagating malformed-metadata errors remain. Dynamic relation cardinality, block-type expansion/fingerprints, config collections, plugins and whole runtime manifest metadata remain dependent features; naming their types does not implement those behaviors.

The [expectation ledger](full-content-transport-ports.json) explicitly selects four validation-issue sets and six manifest sets, preserving every condition from 25 source expressions in 20 adapted Node/local D1 HTTP cases. Three `manifest-build.test.ts:406` conditions already had scalar credit, so 22 source-ID expectations are additional. This is complete selected expectation coverage with adapted setup/envelopes, not whole runtime factory, REST, MCP, Postgres or deployed-hosting parity. The historical 118-file catalog remains unchanged; this separate selection retains committed blobs, hashes and exact expressions. Expanded Node comparisons for one source partial-object matcher earn no extra expression credit.
