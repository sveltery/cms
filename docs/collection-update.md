## Trusted server API

`cmsService(database, principal).updateCollection({ collection, input, expected })` requires `schema:manage` before parsing or touching storage. `collection` is the existing slug. `input` is a strict plain object containing optional `label`, `labelSingular`, `description` and `supports`. Unknown keys reject; no slug/source/version/field/schema mutations are available. Labels reuse the existing trimmed, nonempty, 200-character schema bound; description permits an empty string and at most 2,000 characters. Supports permits the existing `drafts`/`revisions` subset, at most two entries, retaining their order and allowing explicit `[]`. This does not implement revision history or publishing.

Omitted keys and explicit `undefined` preserve stored values. Explicit `[]` clears supports; an empty description persists `''`. Null metadata is invalid, following the existing creation contract. Existing nullable stored singular label/description remain null when omitted. Empty updates still touch the timestamp. Missing collections report `CmsError('NOT_FOUND')`.

`expected` is the existing `{ version, updatedAt }` revision-precondition shape, required at the service boundary. Metadata writes **never increment collection schema version**. Field additions retain their existing schema version CAS. The registry's `updateCollection(slug, input, expected?)` is a low-level trusted API with an optional caller precondition; even without one, an atomic guard compares the observed ID/version/timestamp to prevent an intervening schema or metadata write. The batch contains a guard insert, one metadata `UPDATE … RETURNING`, and guard cleanup. A failed guard maps to `CONFLICT` and rolls back every statement. Other storage errors propagate. The response uses this operation's returned row, so a later writer cannot change its receipt.

No schema DDL/migration, new field types, field/content changes, endpoint, collection page, pager, credentials, provisioning, deployment, release or security configuration is added. Production mutation composition stays default-disabled and the UI stays disabled. Node/local D1 evidence is bounded local storage evidence, not deployed-hosting support.

## Paired real reference and fixture limits

Run `node scripts/reproduce-collection-update-upstream.mjs`. It fetches the complete pinned registry (blob `da7bbcdda224dfca8d9146b2f36659ab90bcac2e`), test file, transaction helper (blob `69bf167998a2fa9cc228c3612a69c8fde5ed85fe`) and raw D1 dialect (blob `b026d293554c5173e1447b5eff0d704e169d3384`), verifies those blobs and the `kysely-d1@0.4.0` tarball, then bundles the unmodified registry class with the **same shared assertion functions**. It executes separate Node/D1 processes because upstream caches transaction capability process-wide. Node uses genuine `node:sqlite` statements with a Kysely-shaped fixture bridge; D1 uses the actual pinned upstream dialect on a real Miniflare binding. Product dependencies are not changed.

Upstream fixtures insert rows directly into a temporary `_emdash_collections` table with the columns consumed by the real update/mapper; they do not execute upstream's complete migrations or collection creation/media activation. Local fixtures use actual CMS migrations and registry creation. The precondition substitution grants no creation/migration/media parity. Upstream `refreshDevTypes` is a no-op, as in the selected source suite's own mock; unrelated registry dependency imports (dialect helpers, identifier validation, media, FTS, transfer, chunks and collection cache) become throwing fixture boundaries. If any selected update invokes them, the reference run fails. Real `withTransaction`, collection types/mapper, URL-pattern helper, Kysely/SQL and D1 dialect remain in use. The script prints the complete boundary list. No FTS search transition, type generation, broader schema operation or production application initialization is claimed.

The paired run passed **10 cases**: six selected source cases plus four supplemental probes across Node/local D1. Probes confirm omitted/undefined values, singular-label updates, explicit empty description/supports and unchanged SQLite schema objects. Upstream's collection mapper has **no schema version property** and its update does not write a version; the local existing schema-version field remains unchanged. No upstream bug claim was identified.
