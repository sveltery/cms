# Sveltery CMS

A self-hosted, SvelteKit-native content management system. Follow EmDash's relevant behavior with tests ported before implementation; document specific deviations required by SvelteKit. Only verified behavior is claimed, with no blanket binary, plugin, or schema-import compatibility promise.

The project is at its foundation stage. Native server hooks now compose explicitly configured persistent storage with current stored sessions; the [passkey-first identity feature](docs/passkey-setup-login.md) adds first-administrator registration, login and logout. The complete site/seed wizard and enabled content editing remain unfinished. The visible content editor is a disabled schema-driven preview. The UI will eventually consume `sveltery/ui`; isolated temporary Svelte components support early development.

Node.js 24 and pnpm 12.6.0 are the development baseline. Preserve Node and Cloudflare hosting options. The [persisted schema API](docs/full-schema.md) recognizes all 17 pinned field types and stores collection metadata, field validation/default/widget/options, and indexing/translation flags. Actual draft writes use the pinned validator and preserve numeric, boolean, array and object values through storage. Forward migrations preserve v1/v2 content while expanding metadata and registering empty identity tables. The bounded [schema administration UI](docs/schema-admin.md) still exposes collection creation, additive string/text fields and [scalar metadata editing](docs/field-edit.md) through native remote forms; broader field controls are unfinished. [Configured runtime storage](docs/runtime-composition.md) enables the existing server mutation gate unless `SVELTERY_MUTATIONS_ENABLED=false`; every write still requires a current stored session and its operation permission. Unconfigured hosting keeps writes unavailable. Configured Node/SQLite and the [official Cloudflare Worker](docs/cloudflare-runtime.md) have local persistence and stored-session HTTP evidence. Cloudflare D1 sessions, bookmarks and query coalescing are implemented; deployment, Durable Objects and Hyperdrive remain future scope. Registered content remotes compose the database service with collection-qualified schema data and opaque revisions.

Run `sh scripts/bootstrap.sh` for frozen installation, checks, service/development tests, build, registered production remote tests, explicit Node package checks, and the official Cloudflare build/source/artifact checks. Hosted CI runs the browser suite against both preview and standalone Node with Chromium sandboxing enabled. The editor remains disabled, and unauthenticated remote requests fail closed.

No deployment, cloud resources, secrets, or package publishing are part of repository setup.

For a standalone local Node process, use `pnpm build:node` then `HOST=127.0.0.1 PORT=3000 ORIGIN=http://127.0.0.1:3000 SVELTERY_DATABASE_PATH=./data/cms.db pnpm start:node`. The first configured request opens and migrates the persistent file; the exact public origin is trusted host configuration. `pnpm package:node` stages an isolated runtime package for a frozen production-only install. See [the Node hosting contract](docs/node-hosting.md) and [runtime configuration](docs/runtime-composition.md) for commands, source references, packaging contents and limitations. This explicit target leaves default adapter-auto builds intact. For local D1 hosting, use `pnpm build:cloudflare` then `pnpm start:cloudflare`; the [Cloudflare contract](docs/cloudflare-runtime.md) documents trusted bindings, local Worker evidence and pending deployment scope. Use `/setup` for first-administrator passkey registration, then `/login`. The full site/seed wizard and writable content UI remain incomplete.
